# Agent instructions

Точка входа. Читать при старте сессии, в этом порядке.

## Порядок чтения

1. `docs/memory/PROJECT.md` — что за проект, архитектура, модель данных
2. `docs/memory/STATE.md` — где мы сейчас, что в работе
3. `docs/memory/CONVENTIONS.md` — как писать код
4. `docs/memory/BACKLOG.md` — что отложено, known issues
5. последние 2–3 файла из `docs/memory/iterations/`
6. `docs/memory/DECISIONS.md` — если предстоит архитектурный выбор

## Правила работы

- **Не дублировать.** Состояние проекта живёт только в `STATE.md`.
- **Ссылаться на код.** В файлах итераций указывать конкретные файлы и функции.
- **MEMORY ≠ SPEC.** «Как есть сейчас» — в `STATE.md`, «как должно быть» — в `docs/spec/` (если появится).

## End of iteration checklist

1. Все тесты проходят
2. Обновить `docs/memory/STATE.md` (Done / In progress / Next / Blockers)
3. Создать `docs/memory/iterations/YYYY-MM-DD-NNN-<slug>.md` по шаблону
4. Если было архитектурное решение — дописать в `DECISIONS.md`
5. Если появился TODO или техдолг — дописать в `BACKLOG.md`
6. **Проверить память на противоречия.** Новое знание может опровергать
   записанное ранее. Если так — исправить во ВСЕХ файлах, а не только в `STATE.md`.
   Именно так устаревшее «Playwright не установить» осталось в `PROJECT.md`
   после того, как выяснилось, что он работает.
7. `git add -A && git commit -m "iter NNN: <summary>"`

## Критично для этого проекта

- **Деплой через сборку образов.** Бинд-маунтов нет: правки кода в контейнер не попадают.
  Нужно `docker compose build <сервис>` и `docker compose up -d --no-deps <сервис>`.
  Копирование через `docker compose cp` работает до первого пересоздания контейнера.
- **Проект требует дисциплины по памяти хоста.** Свободной RAM мало, тяжёлые прогоны
  срываются. Подробности — в `PROJECT.md`, раздел «Ограничения окружения».
