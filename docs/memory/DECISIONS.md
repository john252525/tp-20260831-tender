## ADR-001: Ollama вынесена в отдельный сервис

**Дата:** 2026-09-17

**Контекст.** Ollama считала эмбеддинги для семантического фильтра тендеров.
Работала в том же docker compose. При пиках памяти ядро убивало llama-server (OOM),
из-за чего падал семантический анализ: тендеры уходили в UNCERTAIN с ошибкой.

**Решение.** Вынести Ollama в отдельный репозиторий tp-20260831-tender-ollama
как автономный микросервис. Проект подключается по EMBEDDING_SERVICE_URL.
Локальный контейнер закомментирован как аварийный резерв.

**Последствия.** Крупнейший потребитель памяти убран с хоста проекта. Один сервис
эмбеддингов может обслуживать несколько проектов. Появилась внешняя зависимость:
при недоступности сервиса семантика не работает (но конвейер не падает — тендер
остаётся в UNCERTAIN для повторной обработки).

**Альтернативы.** Проброс GPU — отклонено, в хосте только virtio GPU без ускорения.
Переезд на другой сервер — отложен, ждёт адреса.

## ADR-002: Состав закупки берётся из API ГосПлан, а не из документов

**Дата:** 2026-09-17

**Контекст.** Позиции и цены тендера можно получить двумя путями: скачать документы
и распарсить (LLM), либо взять структурированный блок notificationInfo из детального
ответа ГосПлан API.

**Решение.** Приоритет у API. LLM-извлечение структуры запускается только если
позиций ещё нет.

**Последствия.** Позиции появляются мгновенно и точно, без LLM и без скачивания
файлов. Работает даже при недоступном zakupki.gov.ru. LLM больше не затирает
корректные данные.

**Альтернативы.** Только документы — отклонено: zakupki.gov.ru недоступен с хоста,
а LLM-извлечение дороже и менее точно.

## ADR-003: Статус тендера выводится из фактов, а не выставляется вручную

**Дата:** 2026-09-17

**Контекст.** Статус присваивался разрозненно в нескольких местах. READY_FOR_DECISION
не выставлялся нигде, поэтому финальный шаг (передать человеку) был недостижим.
Плюс GET /tenders/{id} отдавал пустой список поставщиков.

**Решение.** Единая функция recalculate_tender_status() выводит статус из состояния
лотов и КП. Пороги берутся из настроек. Ручные решения (APPROVED, REJECTED)
защищены от перезаписи автоматикой.

**Последствия.** Финальный шаг достижим. 14 лотов перестали бесконечно висеть
в CP_REQUESTED. Статус всегда отражает реальность.

**Альтернативы.** Выставлять статус в каждой точке изменения — отклонено,
именно так и возникла рассинхронизация.

## ADR-004: Маржа считается по фактам, а не заглушкой

**Дата:** 2026-09-17

**Контекст.** Для всех тендеров маржа была равна 50 (margin_fallback_score),
то есть отбор лучших по прибыли был случайным.

**Решение.** Расчёт по достоверности: фактические КП, затем средняя маржа по
категории, затем настройки. Учитываются только содержательные КП (FULL, PARTIAL).
Порог из настроек соответствует 60 баллам, двукратное превышение — 100.

**Последствия.** Ранжирование стало осмысленным. Пустое КП (статус NONE) больше
не даёт фиктивную маржу 100 процентов.

## ADR-005: Деплой через пересборку образов

**Дата:** 2026-09-17

**Контекст.** В docker-compose.yml нет бинд-маунтов, код копируется в образ через
COPY. Правки, скопированные через docker compose cp, жили до первого пересоздания
контейнера. При docker compose up -d контейнеры пересоздались из старых образов,
и весь код итерации пропал из контейнеров.

**Решение.** Любая правка кода требует docker compose build и последующего
up -d --no-deps. Копирование через cp допустимо только для быстрой отладки.

**Последствия.** Деплой медленнее (сборка), но результат воспроизводим.
Это зафиксировано в AGENTS.md как критичное правило проекта.

## ADR-006: Автооркестрация через Celery beat, а не ручной запуск

**Дата:** 2026-09-17

**Контекст.** Расписание beat состояло из одной задачи (приём почты). Конвейер
запускался только вручную через API, поэтому данные накапливались в начальных
статусах: 891 тендер в NEW, 23 задачи навсегда зависли в PENDING.

**Решение.** Восемь периодических задач: синхронизация источников, обработка новых,
присмотр за зависшими, восстановление упавших, запуск конвейера для лучших по скору,
напоминания, торг, приём почты. Каждая идемпотентна и пропускает занятые сущности.

**Последствия.** Конвейер работает автономно: за сессию тендеров стало 1243 -> 3608,
позиций 0 -> 10628. Обработок PROCESS_TENDER 349 -> 2591. Без ручного вмешательства.

**Отклонённые альтернативы.** Запуск всего одним «умным» cron — отклонено,
задачи должны быть раздельными и перезапускаемыми по отдельности.

## ADR-007: E2E проверяется реальным браузером, а не только jsdom

**Дата:** 2026-09-17

**Контекст.** UI тестировался через jest и jsdom на реальных ответах API.
Такой тест показывал, что страница корректна. Но когда закупка с 11 014
позициями попала в реальный браузер, он упал по OOM: ядро убило процесс
(`Out of memory: Killed process chrome-headless`). jsdom не рендерит
по-настоящему, не потребляет память и не воспроизводит поведение
браузера — проблему он не видел.

**Решение.** Тяжёлые страницы проверять реальным браузером через Playwright.
Скрипт `frontend/e2e/live-card-check.cjs` выбирает большую и маленькую
закупку, открывает карточку, проверяет рендер и ловит ошибки JS.

Запускать **с хоста**, не из контейнера: в alpine нет glibc, бинарники
Chrome не стартуют. Использовать `chrome-headless-shell` — полный chromium
падает по OOM на больших страницах.

**Последствия.** Проблемы рендера обнаруживаются до пользователя.
Это дополняет, а не заменяет jsdom: быстрые проверки логики остаются в jest,
проверка тяжёлых страниц — в браузере.
